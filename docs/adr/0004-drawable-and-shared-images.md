# Drawable and shared Images

Applications submit rectangles, positioned sprites, and custom compositions through `Frame::draw(&drawable)`: separating reusable `Image` handles from editable `Sprite { image, x, y }` descriptions lets multiple sprites share a picture while retaining independent placements, and the public `Drawable` trait lets applications compose existing primitives through the same interface.

This explicitly supersedes ADR 0003's loading API, Sprite-as-resource model, and lazy GPU upload (`Image::load(ctx, path)` replaces `Sprite::load(path)` and `Frame::draw()` replaces `Frame::draw_sprite()` without compatibility wrappers). Loading synchronously decodes the PNG and queues a GPU upload through the initialized context, moving upload preparation out of the first draw. GPU execution need not finish before loading returns. This requires loading during game construction or play rather than before engine startup, and loaded images consume GPU resources even before being drawn. The public constructor belongs to `Image`; graphics upload helpers remain internal.

Image clones share GPU resources belonging to the loading context, and drawing with a different graphics context returns an error. Decoded CPU pixels are released after upload is queued; automatic re-upload to another device is not supported. The existing loading-error mechanism, independent loads without a path cache, and resources releasable after the final owning handle is dropped remain.

Primitive submissions capture current values and image handles so later edits, image replacement, or dropping descriptions leave prior drawing intact; recorded frames retain resources until cleared or dropped, compositions preserve submission order, and natural dimensions, transparency, logical coordinates, top-left anchoring, DPI scaling, clipping, and non-finite-position rejection remain, as do ADR 0001's lifecycle and ADR 0002's Game callback and engine-managed GPU ownership and presentation.
